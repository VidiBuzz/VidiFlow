How Mez profiles, config, and model providers relate

Every named profile is a complete, isolated Mez home. One process switches homes by re-pointing HERMES_HOME, and from that moment every config file, secret, skill, session, and provider plugin resolves inside that home. Nothing leaks in from a sibling profile, and that is deliberate.

Measured on  vidi Mez  v0.21.5+7024.g7653424 Verified against live file:line checks, Oct 2026

00The one-sentence model

If you remember one thing, remember this.

A profile is a Mez home. Invoking hermes -p lexi sets HERMES_HOME to ~/.hermes/profiles/lexi/ before any code imports, so config.yaml, .env, skills/, sessions/, memories/, and plugins/ all read from that directory. There is no cross-profile inheritance and no global provider registry for user plugins. A provider installed under one home is invisible to every other home, by design.

Mechanism, in order: hermes_cli/main.py:594 pre-parses -p/--profile and rewrites HERMES_HOME before imports; profiles.py:2572-2589 maps default to the root home and anything else to root/profiles/<name>; every subcommand accepts -p, and a sticky ~/.hermes/active_profile supplies the default when no flag is given. Example verified live: hermes -p vidimail config path returns the vidimail profile's own config.yaml.

01What each profile owns, and what it shares

A named profile directory is a full copy of the Mez home layout, not a overlay with a few personal settings. Almost everything is isolated; only shipped bundle code, the admin-only managed scope, and the sticky default-profile pointer are per-box.

ArtifactScopeShared or isolated, and why
profile.yamlisolated Metadata about the profile: display name, description, kanban role, UI meta. Written by hermes profile describe/rename. Not configuration.
config.yamlisolated The entire file, per profile. Merged over DEFAULT_CONFIG, then the managed overlay. The root ~/.hermes/config.yaml is never merged as a fallback for a named profile.
.envisolated Profile-scoped secret scopes exist precisely so one profile's keys never reach another's. Seeded at profile creation; legacy profiles were backfilled once with a copy of the root .env. ${VAR} refs in config resolve through the profile's own scope; a miss is a miss.
skills/isolated Per-profile copies; bundled skills are re-seeded into each profile at update time. Diverge freely per profile.
sessions/ & state.dbisolated The canonical session store is per-home.
memories/isolated Per-profile memory namespace.
plugins/isolated User-installed provider plugins live here, per home. This is the crux of §02.
models/ cache, auth.jsonisolated Per-profile model caches and credentials.
Bundled provider pluginsshared Shipped in the repo at plugins/model-providers/<name>/, available to every profile (openrouter, anthropic, deepseek, nvidia …).
Managed scopeshared /etc/hermes/ (or $HERMES_MANAGED_DIR) is a read-only admin overlay merged into every profile's config. Admin-only; not configured on this box.
active_profileshared One stick of global state: remembers which profile is the default when no -p is passed. hermes profile use <name>.

Config precedence, verbatim from hermes_cli/config.py:2123-2127: DEFAULT_CONFIG + profile config.yaml + managed scope, env-expanded. Two routing rules matter in practice: ${VAR} references resolve through the profile's own secret scope only, and UPPER_SNAKE keys passed to hermes config set are routed to .env, not config.yaml.

03Why a provider added to profile A does not appear on profile B

Provider plugins come from four discovery sources, and only two of them are shared. The lookup chain binds to the current profile's home layer first and never borrows across homes.

Bundled plugins · shared

Shipped inside the repo, plugins/model-providers/: openrouter, anthropic, deepseek, nvidia, openai-codex and about 40 more. Loaded once per process, visible to every profile.

User plugins · per home

$HERMES_HOME/plugins/model-providers/ resolves against the active profile at lookup time and loads into "that home's own layer", keyed by home path. Two threads serving two profiles must not cross-register.

Pip entry points · shared

hermes_agent.plugins entry points, process-wide. Plus per-profile named custom providers in config.yaml, memoized per home so multiplex homes never borrow each other's answers.

Why profiles are isolated by design

The database comment at kanban_db_dispatch.py:2831 and the secret-scope design at agent/secret_scope.py say it plainly: one process serves several profiles (the multiplex gateway, Desktop serve, the kanban dispatcher), so a leaking layer would leak everyone's credentials and settings into everyone's agents. Profile-scoped secrets, scrubbed spawn environments, and per-home plugin layers exist so that a multi-tenant box behaves like several tenants with a single install.

That is why there is no "add once, see everywhere" path. The supported shared mechanisms today are exactly three: repo-bundled plugins (ship with hermes update), the managed scope (/etc/hermes/, admin-pushed, merged into every profile), and the sticky active_profile pointer. Everything else is per-home.

04Supported ways to make a provider available to all profiles

There is no sync verb and no inheritance. Pick one of these, all verified against hermes --help on this version.

A · Copy the plugin into every profile home

for p in $(hermes profile list | awk '/^[ ]/ {print $1}'); do
  mkdir -p ~/.hermes/profiles/$p/plugins/model-providers
  cp -r ~/.hermes/plugins/model-providers/cheaperinference ~/.hermes/profiles/$p/plugins/
done

Discovery re-scans the plugin dir on a TTL, so a served profile picks it up without a restart. Cost: every future profile needs the copy again.

B · Set each profile's config explicitly

hermes -p agent_army config set model.default deepseek-v4.1-flash
hermes -p agent_army config set model.provider cheaperinference
hermes -p agent_army config set model.base_url 'https://api.cheaperinference.com/v1'

# UPPER_SNAKE keys route to .env, and .env is per profile:
hermes -p agent_army config set CHEAPER_INFERENCE_API_KEY <key>

C · Clone new profiles from a good one

hermes profile create <newname> --clone-from lexi   # copies config.yaml/.env/SOUL.md/skills
hermes profile create <newname> --no-skills          # bare profile, no bundled skills

Bot tokens are stripped on clone by default; --clone-channels keeps them, but two profiles sharing one bot token collide. Existing profiles are not touched by clone.

D · Managed scope, the true all-profile layer

Put config.yaml and/or managed.env under /etc/hermes/ and every profile, default and named, merges it. Blunt but real: no per-profile opt-out, and it is not configured on this box yet, so using it would be a new decision.

Checked, not assumed

None of these exist in this version: a global or shared user-provider directory; include:/extends: config inheritance; hermes config set --for all-profiles or any provision/sync verb; or HERMES_VAR shell-env inheritance, which is scrubbed at spawn rather than propagated. Traced across providers/__init__.py, hermes_cli/config.py, and hermes profile --help.

05My provider is missing

Run the three checks in this order. Each one narrows the failure before you touch anything.

Three checks, in order

1

Which profile am I actually in? Confirm your home resolves to the profile you expect: hermes -p <profile> config path. If you launched without -p, a sticky ~/.hermes/active_profile may be choosing for you. A missing provider under profile B is usually here: it was installed under the default home, not under B.

2

Does the plugin dir exist in this profile's home? Look for <profile-home>/plugins/model-providers/<name>/ with a plugin.yaml inside. On vidi, cheaperinference lived only under ~/.hermes/plugins/… (the default profile) and was absent from all 8 named profiles. If it is not there, copy it (§04 A).

3

Does the profile's config actually name the provider, and is the key in scope? Check model.provider/model.base_url in <profile-home>/config.yaml, and the API key in <profile-home>/.env — never another profile's .env, since a scope miss is a miss by design. Set both with hermes -p <profile> config set (§04 B).
