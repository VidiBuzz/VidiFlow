Snap Judges

A typed answer in one forward pass, with no generated prose beside it.

You have spent two years getting used to asking a language model a question and reading prose back. This is the other shape. You hand the engine some state and a question whose answer is already typed — a choice, a score, or a yes/no — and it hands back that answer with a probability, in one pass, without writing a single word.

Mez stays the deliberative brain for reasoning, tools, memory, and voice. A Snap Judge is the reflex beside that brain, so routine routing does not pay for a full generation.

What it actually is

A language model is a next-token predictor. You give it text, it gives you text back, and if you want a decision you have to parse the text into a decision. A Snap Judge inverts that. You give it state — a ticket, an email, a JSON document — plus typed questions, and it gives you typed answers with probabilities.

There are three primitives, and they are the whole vocabulary. Nothing else exists.

✓

Choice

Pick one option from a list you supply. Returns the chosen option, a probability for every option, and a confidence. Jev allows up to 255 options.

◫

Score

Place the state on an ordered rubric of two to ten levels. Returns a continuous score, the distribution across levels, and a confidence.

?

Noul

Is this statement true of the state? Returns the probability that it is, from 0 to 1. The cheapest and most reliable of the three.

The whole request is one forward pass. All questions are evaluated in parallel against the same state, so adding questions barely changes latency. That is what makes a batch of five routing decisions cost about the same as one.

Here is the entire idea in one request:

resp = requests.post(
    "https://openrouter.ai/api/alpha/decisions",
    headers={"Authorization": f"Bearer {OPENROUTER_API_KEY}"},
    json={
        "model": "typesafe/jev-1.13",
        "state": "Hi, we were billed twice for March. Please refund the duplicate today.",
        "questions": {
            "department": {"type": "choice", "criteria": {
                "billing": "invoices, refunds",
                "technical": "bugs, outages"}},
            "urgency":    {"type": "score",  "criteria": ["not urgent", "soon", "blocking"]},
            "churn_risk": {"type": "noul",   "instructions": "Does the user threaten to cancel?"},
        },
    },
)
# -> {"department": {"choice": "billing"}, "urgency": {"score": 0.71}, "churn_risk": {"noul": 0.88}}

No prompt engineering. No respond only with JSON. No parsing step. The answer is a number your code branches on.

What it is not

It is not a smaller language model. There is no chat model behind it that you can prompt. It cannot write a paragraph, explain itself, or reason about anything beyond the question you asked.

It cannot hallucinate — but read that carefully. TypeSafe put it plainly in their own launch post:

“Our number is not empirical. Schema matching is guaranteed, thus we can confidently add 0% into the plots.”

TypeSafe AI, Introducing System One Models & Jev, 15 September 2026

Every answer is a valid option. It cannot invent a label. But it can absolutely pick the wrong valid label. Type safety removes a class of integration bugs. It does not remove misclassification. If you adopt it expecting it not to be wrong, you have misread the claim.

It reads instructions literally. This is the failure mode that catches people. On the same support ticket, refund scored 0.72 and not a refund scored 0.47. TypeSafe lists nine known jagged edges for version 1.13; the ones that matter for VidiFlow are literal reading, arithmetic and dates, option ordering, and large irrelevant state. Their own guidance is blunt about the first one: Jev answers the question you wrote, not the one you meant.

One clarification worth having, because it changes how you read every benchmark: the decision not to generate text is not new. Label-likelihood scoring is in GPT-3 §2.4 from 2020, MMLU §4.1 from 2021, and verbalizers from 2021. The audit below calls the contribution plainly: the visible contribution is the packaging — a typed API, one hosted endpoint, output priced at zero, and many questions against a single input. That is not a criticism. Packaging is exactly what turns a research trick into infrastructure you can adopt on a Tuesday.

Where it genuinely wins

The valuable property is not raw accuracy. It is knowing when it is wrong — which is exactly what an automation layer needs.

When Jev is wrong, its confidence drops to around 0.66–0.69. When the cheap LLM is wrong, it still reports 0.82–0.85. The LLM’s verbalized confidence is high almost all the time; Jev’s confidence carries more information about its own errors.

PavelRavvich/jev-bench — independent benchmark, $1.13 total spend

On spam detection, Jev’s top 90% most-confident predictions were 100% correct, against 98.9% for the LLM. That is the property you need: a threshold above which you can act without review.

And the architecture that follows from it

Put the judge in front and let it decide what deserves thought. TypeSafe documents this themselves as confidence-gated routing; all three independent benchmarks converge on it.

Measured on the shared 130-message subset: on spam, the cascade matched the frontier model’s accuracy exactly while sending only one message in nine to the expensive model — 8.5× cheaper and over 5× faster at the median. On Banking77 it gave up 1.6 accuracy points for a 5.5× cost reduction.

One counter-intuitive caveat. Cascading into a cheap LLM does not pay for itself. On Banking77, Jev plus a cheap LLM cost more than the LLM alone, because both cost about the same per call. The cascade earns its money only when the model behind it is expensive. Plan the architecture around that, not around the headline.

Calibration, and the one fix

This is where adoption decisions actually get made, and the picture is more nuanced than either the hype or the debunk suggests.

Out of the box, on familiar English tasks, Jev is the best-calibrated option measured. Median ECE of 0.071 on a 13-subset public suite — better than Nimble-9B on 11 of 13 subsets, and better than every Gemma 4 variant (0.114–0.180) before any fitting. Against LLMs that write their confidence as a number in text, Jev usually wins.

But the direction of the error changes with the data. On public multi-class sets Jev is overconfident: on GoEmotions, labels it scored between 0.80 and 0.95 matched the human label only 15% of the time. On crash narratives it is underconfident. Within one judge study, refit temperatures ranged from 0.65 to 4.45, and the authors concluded no single temperature fits.

And against models that return real probability distributions, Jev is the worst-calibrated. Its ECE was highest in Janardhan’s run (0.161) and in a nine-model Banking77 pilot (0.138).

There is also an API artefact worth knowing before you build: the API rounds every probability to 0.01, and in one committed sample 70.4% of choice probabilities came back as exactly zero. Noul is clamped to 0.01–0.98. If you plan to threshold on very small probabilities, design around that.

The fix is small and it is not optional. A small refit corrects most of the calibration error, for Jev and for any open model read the same way:

  • A two-parameter refit on civil_comments took Jev’s ECE from 0.16–0.21 to under 0.025 on held-out data
  • Transferring a fitted slope and refitting only the intercept on 50 labels cut mean ECE by 74%
  • One temperature fitted on 50 labels brought plain Gemma 4 26B from 0.180 to 0.080

Budget 50–300 labelled decisions per question family and fit a temperature on them. Every independent reviewer reaches the same conclusion. The open replicas report the same order of correction: Nimble fitted 2.179, Luce 2.5–3.3.

LLM or Snap Judge?

Here it is plainly.

Use a Snap Judge when…

  • The answer is a choice, a score or a boolean that you can write down in advance, before you build
  • You need an answer in hundreds of milliseconds or less, somewhere a user is waiting
  • You branch on the result — routing, triage, guardrails and escalation paths
  • You have no labelled data yet and still want to ship something working this week
  • The data cannot leave your network
  • You need the answer guaranteed to match your schema, with no parse failures at all

Use an LLM when…

  • The output has to be prose, code, or something genuinely open-ended and unbounded
  • The task needs real reasoning, arithmetic, date maths or several steps of indirection
  • You need the model to explain itself
  • The label space is large, fuzzy in its edges, or it shifts on every single call
  • You still do not know what the correct labels should even be named

The label-space warning is not theoretical. On Banking77 at 77 options, Jev scores 0.870 while Laya scores 0.425 — because options share a fixed token budget, so at 77 options each label gets three or four tokens and the text stops being distinguishable. That is an architectural limit, not a tuning miss.

The honest answer is neither. The cascade beats both, and it is the one architecture every independent benchmark converges on. A Snap Judge is a reflex. An LLM is deliberation. You are not choosing between them — you put the reflex in front and let it decide what deserves thought.

The cost of being wrong here is asymmetric in a way that should settle it for VidiFlow: a judge that abstains has cost you one cheap call. An LLM asked a routing question and confidently wrong has cost you a full generation and a user who saw the wrong answer.

The open-source wave

Nobody predicted this. Within roughly 48 hours of Jev’s launch, at least six independent open clones appeared, and the community now tracks 564 projects across 18 categories in awesome-jev.

They could all exist because the mechanism is not proprietary. End the prompt where the answer would start, take the model’s scores for only the allowed label tokens, and softmax over them. Any open model can be read this way — vLLM exposes it via logprob_token_ids, SGLang via /v1/score.

The most valuable trick in the whole field costs nothing and is model-independent. From the Nimble README: write two nearly identical records and flip one fact so the correct answer flips — a refund signed by Mira is authorised, the same record signed by Noah is not. That is contrastive curation, and it isolates exactly the decision boundary you care about.

The open-source pick

The roles below are the 24 September 2026 adoption decision for vidiflow.net. Snapshot figures are quoted from that date and are not a live service level for the site. Two figures have been corrected from primary sources during this research pass, and are marked.

01

Production core · Apache-2.0

Laya

Laya is the production core. It is pip-installable, it covers more than one hundred languages, and it serves a Jev-wire compatible server with a language router, batching, and hooks for audit, redaction and cache. The English and multilingual encoders are 322 to 421 million parameters. On a T4 it measures 32.8 ms for a single question and 7.2 ms per question when batched at ten, reaching 103–332 questions per second.

A typed-decisions fine-tune in the snapshot moved accuracy from 0.362 to 0.766, with XNLI English at 0.860, and 48 of 51 languages were measured usable at more than three times random. That size is why the report places it on one RTX 4090 beside LM Studio, Qdrant and LiveKit.

NandhaKishorM/laya

02

Accuracy pilot · Apache-2.0

Kev-4B

Kev-4B is the accuracy pilot, not the default server. On new sources in the snapshot, Kev-27B lands within about one point of hosted Jev, and both Kev-4B and Kev-9B land within about four. The four-billion-parameter checkpoint is the one to fine-tune on VidiFlow tickets. It has to run under Python 3.12 or 3.13, because torch had no wheels for the repository standard of Python 3.14. Promotion happens only where the gain stays above two points on held-out labels.

03

Browser and edge demo · MIT

SemIf

SemIf, formerly OpenJev, is the browser and edge demo. It runs on a home RTX 3090 and includes a WebGPU demo with no waitlist. Shared-state prefill reaches twenty decisions a second, and twenty-one questions take one second on a 3090 compared with 5.3 seconds on the JSON path. On the measured subset, SemIf trails hosted Jev by about four points, so the report keeps it as the public teaser and the home-lab path rather than the production core.

TheoLeeCJ/SemIf

Read this before you deploy Laya. Its base checkpoints are near chance: 0.362 and 0.352 against a 0.318 random baseline and a 0.461 majority-class baseline. Laya is a fast base to specialise, not a zero-shot decision engine. All of the 0.766 comes from fine-tuning. Skip fine-tuning and you are running something worse than guessing the most common label.

Two more traps from its own documentation:

  • Serve it with Router(preload=True). By default the router keeps one checkpoint resident, so traffic that alternates languages rebuilds a model on every request — a measured 7.4 s median on CPU and 10.3 s on a T4. That turns a 33 ms model into a ten-second one.
  • Watch the option budget. head_max_len is a cap, not a head length. Past roughly head_max_len / 4 options the head grows beyond the cap and your state gets truncated rather than merely shortened.

What does not become the core

jevlike, mini-jev and jeff are not the production core. jevlike remains a research starter with a weak byte encoder. mini-jev is a teaching bench, and the field-type rules stay useful without adopting that repository. jeff is only a cheap fallback if Laya cannot run, and only for easy triage. Nimble contributes a contrastive curation method, and it is not the server.

Recommended adoption

Unchanged from the 24 September decision, with this research pass applied. None of it is wired into Mez. Auto-action stays off unless a person confirms the result.

  1. 01

    Label first. Export 300 to 500 labelled decisions for route, escalate, urgency, churn and refund, keeping each family together. Score Laya, Kev-4B and SemIf before any of them serves traffic. Per the calibration finding, 50 to 300 per family is enough to fit a temperature; 300 to 500 across families lets you compare checkpoints.

  2. 02

    Serve Laya correctly. Install beside the existing agent backend, and use Router(preload=True) — without it, alternating-language traffic costs seven to ten seconds per request. Reach that server only through the site proxy.

  3. 03

    Fine-tune or do not ship. The base checkpoints sit below the majority baseline. Fine-tune on VidiFlow pairs, fit temperatures on those labels, set a threshold for each question, keep an explicit abstain option, and build the training set with Nimble’s contrastive-pair method.

  4. 04

    Keep the pilot and the teaser. Run Kev-4B in a separate Python 3.12 or 3.13 environment, and offer SemIf as a no-backend teaser on the vidiflow.net demo and on the /lex page.

Constraints already on the table for today

  • 01

    Today’s machine has one RTX 4090 with 24 GB, shared with Qwen3.6-27B at 15.4 GB plus KV cache, and two RTX 6000 Pro cards are the later plan.

  • 02

    States longer than about four thousand tokens are shortened first, or they go to a longer-context checkpoint and get tested again. Laya’s multilingual build reads to 8,192 with max_len=8192.

  • 03

    Published temperatures do not transfer. Each threshold is refit on VidiFlow labels, because published temperatures ranged from 0.65 to 4.45 across independent studies.

  • 04

    Jev and TypeSafe remain their owners’ marks. These open projects follow an interface pattern, and none of them is Jev itself.
